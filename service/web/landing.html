An approval is a fact with a timestamp. Settlement is a second event.

Between the two, the facts the approval rested on can change. The standard does not re-read them.

At evaluation

  • yesThe client funds the job.

    The budget is escrowed by the core contract.

  • yesThe provider submits a deliverable.

    The job moves to Submitted.

  • yesAn evaluator signs off.

    Against the proof of agreement, and only the evaluator can.

  • yesSettlement pays the provider.

    Or refunds the client, if the job is rejected or expires.

At release, unchanged by the standard

  • noA newer observation exists.

    Someone re-read the same subject. The approval still points at the old version.

  • noThe provider was disqualified.

    Qualification can be revoked between evaluation and payout.

  • noThe reading went stale.

    The freshness bound lapsed while the job waited for settlement.

  • noNo approval is bound.

    Nothing ties the payout to a specific evaluation.

Ten clauses, and every one of them is machine-checkable.

One view function holds the predicate. The hook calls it on the release path and the service calls it for its own decision, so there is no second implementation for them to disagree about.

What a refusal looks like

  • 01The simulation returns wouldRevert: true with the reason decoded from the hook's own error type, not the core's.
  • 02The gate reverts the release call, so the payout and the status change unwind together.
  • 03Nothing is broadcast, because the simulation is what decides whether there is anything to broadcast.

The gate is not advisory.

It is a hook on the release path itself. The core calls it while the job is still Submitted, before the status changes and before any transfer, so a refusal takes the payment with it.

// erc-8183 core, abridged. The hook call is the gate.
// the selector is the public complete(), which calls this helper.
function _complete(
    address actor,
    uint256 jobId,
    bytes32 reason,
    bytes calldata optParams
) internal {
    Job storage job = jobs[jobId];
    if (job.status != JobStatus.Submitted) revert WrongStatus();
    if (actor != job.evaluator) revert Unauthorized();

    bytes memory data = abi.encode(actor, reason, optParams);
    _beforeHook(job.hook, jobId, this.complete.selector, data);

    job.status = JobStatus.Completed;

    uint256 amount = job.budget - job.settledAmount;
    uint256 net = amount - platformFee - evalFee;
    _payout(jobId, job, net, this.complete.selector, optParams);

    emit JobCompleted(jobId, actor, reason);
    _afterHook(job.hook, jobId, this.complete.selector, data);
}
  • It runs before the status change.

    The job is still Submitted when the gate is called. A revert unwinds the entire call, so there is no window in which the job looks complete and the payment has not happened.

  • And before the payout.

    The platform fee, the evaluator fee and the provider payout all sit after the hook returns. Refusing the release refuses all three.

  • Refunds are deliberately not hookable.

    The core documents claimRefund as not hookable. A gate that could block a refund could trap a client's money, so that path is closed to it by construction.

What is real, and what is not.

A gate that gets its own claims wrong is worth nothing, so the gaps are listed here rather than left to be found.

Real, with an artifact behind it

  • okTen contract tests pass against the real ERC-8183 core on a UUPS proxy, not a mock.
  • okFour invalidation classes proven live, each with the release refused and the balance unmoved.
  • okKeeperHub simulates, broadcasts and is read back, with the execution id recorded.
  • okThe service drives its own release over HTTP, and the reconciliation of a held job ends in a completed execution.

Not done, and named

  • -Clause 8, the provenance comparison, is declared in the specification and not enforced in the predicate.
  • -The contracts are not verified on Basescan, so the source is not published there.
  • -Testnet only. Nothing here has touched mainnet or real funds.
  • -The ACP agent identity exists but is not wired into this flow. These are ERC-8183 jobs, which is the standard ACP implements.
  • -No scheduler. A held job waits for someone to reconcile it.

Run it locally.

Nothing here needs a hosted service. The contracts build from source and the proof scripts read their configuration from the environment.

bash Base Sepolia, chain 84532 
git clone https://github.com/subheeksh5599/duality && cd duality

# contracts. lib/ is gitignored, so install the two upstream dependencies.
cd contracts
forge install erc-8183/base-contracts --no-git
forge install OpenZeppelin/openzeppelin-contracts --no-git
forge build && forge test

# the service, which serves this page and the dashboard
cd .. && python3 -m venv .venv && .venv/bin/pip install web3
cp .env.example .env && $EDITOR .env
export DUALITY_ENV=.env
.venv/bin/python service/duality_service.py --port 8787

# then open http://127.0.0.1:8787/dashboard
